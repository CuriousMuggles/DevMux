# 新手使用与发布需求（历史，v3.1.2 时点）

> 内部历史文档，不随发布包分发，不再维护。记录 2026-10 那次「让新用户能直接拿到可用发布包 + 补 MCP 插件管理」的需求与验收口径；其中提到的路径、提交号和版本号都已过期。现行发布流程见 [发布流程.md](发布流程.md)，用户文档见 [使用说明](../../使用说明.md)。

## 背景和目标

从 GitHub 获取 DevMux 的新用户应能直接找到对应版本的 Windows 程序、全部官方插件和使用说明，按说明启动并安装插件；开发者应能确定发布文件对应的源码版本。本需求包含 MCP 插件管理能力和重新发布。

## 已核实的问题

- v3.1.2 Release 提供程序 ZIP、eBPF 插件和校验文件，但缺少 USB 继电器、DB 烧写、米家插件和完整使用说明。ZIP 内只有 EXE、eBPF、简短发布说明及校验文件。
- README 快速开始没有明确链接 Release 或说明下载、解压和安装选择；源码使用说明的版本及插件流程存在过时内容。构建说明未完整列出实际依赖及 Android platform-tools 要求，插件构建说明遗漏 eBPF，输出路径和命名也与现行发布规范不符。
- MCP 可以发现并调用已启用扩展，但没有完整的插件管理接口，无法按项目工作流通过 MCP 查询、安装、更新、启停和验证插件。
- v3.1.2 tag 与源码版本号一致，下载文件通过 SHA-256 校验；但仅凭版本号和摘要不能证明发布 EXE 来自对应提交。eBPF 包与 tag 源码重新打包的内容除文本换行符外一致。
- 从源码构建的 EXE 在隔离无窗口启动尝试中未被 MCP 实例发现，原因未确定；不能据此认定发布版正常桌面启动失败。此前相关插件自动化测试 26 项通过，但不代表首次使用流程完成。

## 需求

1. 更新 README 和随发布包提供的使用说明，提供明确的 Releases 链接、支持环境、下载文件选择、解压、启动、插件安装和启用步骤，以及数据目录、升级注意事项和常见排查方法。文档版本和实际行为一致。
2. Release 包含对应版本的 DevMux 可执行程序、全部官方插件（usb-relay、db-flash、mijia、ebpf）和使用说明。官方插件统一由 `release_plugins.py` 构建到 `dist/plugin/`，命名为 `插件ID-版本号.dmp`；正式版和调试版遵守项目发布规范。应用运行数据位于 EXE 同目录 `devmux-data/`，兼容旧配置、插件和凭据及显式指定路径。
3. 为 MCP 补充插件管理接口，覆盖本机插件清单及状态、安装、更新、启用、停用、卸载和结果验证；遵循现有认证、权限、生命周期和远程授权边界，不绕过活动任务保护。按现有架构评估远程支持，不虚报未实现的能力。提供清晰的参数、错误和使用示例。
4. 发布时记录 tag、完整提交 ID、构建环境或构建日志及产物 SHA-256，确保 EXE、插件与源码可追溯；不得只凭版本号声称已证明二进制来源。版本选择应基于实际待发布源码，不能把 3.1.3 源码产物混入 3.1.2 Release。

## 验收

- 从用户视角按公开入口获取并解压发布文件，核对完整清单、版本和 SHA-256；验证普通桌面启动、MCP 连接及通过 MCP 安装、启用、查询、停用至少一个隔离测试插件。说明未验证项和环境限制。
- 检查程序、四个插件、说明和校验清单均随 Release 可获得，文档可引导首次使用；验证源码标签、提交与发布构建证据对应。
- 按项目 AGENTS.md 在独立工作树及分支完成代码修改、构建新包及相关测试；合入主线或正式发布前先构建目标包，按 `python tests/run_all.py` 的顺序运行完整测试。失败、跳过、阻塞均如实报告。
- 用户明确要求根据需求完成修改并重新发布；每次提交（含 amend）前仍须展示完整提交 message 并取得用户明确确认，之后按项目流程继续。不要提前将测试或代码单独合入主线。
- 不要求逐项验收核心设备功能或各插件内部功能；必要的回归测试及发布前全量测试仍按项目规范执行。
