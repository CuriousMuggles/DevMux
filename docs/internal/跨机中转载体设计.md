# 跨机中转载体设计（数据流底座）

> 内部设计文档，不随发布包分发。本文是**评审稿**，未定稿前不改代码。
>
> 与 [跨机中转设计.md](跨机中转设计.md) 的分工：那一份讲**交互约定、状态机、心跳与接管**（控制面与业务语义）；本份讲**传输底座**——把「链路」从单一 SMB 共享目录，抽象成可插拔的数据流载体，使以太网直连与串口直连复用同一套协议层。

## 0. 结论摘要

1. 现有 `relay_carrier.py` 的 `RelayCarrier` 抽象是**半成品**：协议层（`RelayQueue`、`StreamChannel`、`relay_session`、`relay_journal`、心跳）全部直接操作文件系统路径，只有「链路探测/状态」真正走了 carrier。
2. 串口是纯字节流，承载不了「目录镜像 / 文件操作重放」，因此载体抽象必须下沉到**数据流**级别——即 `RelayCarrier` 已定义的「命名消息槽 + 命名增量流」两类语义。这是 SMB / TCP / 串口三者的最大公约数。
3. 方案核心是**把协议层从文件系统路径改为走载体数据流接口**，`SharedFolderCarrier` 保持现状作为该接口的文件系统落地；新增 `TcpCarrier` 与 `SerialCarrier` 共享同一套帧协议底座，只差「可靠性处理」一层。
4. 通过**载体验证矩阵**（shared-folder × tcp × serial 三态跑同一批协议场景）保证协议层与介质解耦，并以**本机自回环**（127.0.0.1 与虚拟串口对）完成双端验证，SMB 全量回归守护零退化。

## 1. 背景与目标

- **目标**：把跨机中转的传输底座做成可插拔，新增「以太网直连（TCP）」与「串口直连（Serial）」两种载体；三种载体共用同一套协议层与业务语义。
- **非目标**：不改变配对、心跳、接管、命令白名单等**业务语义**（见 [跨机中转设计.md](跨机中转设计.md)）；不引入整体框架替换；不改变共享文件夹的既有文件布局与行为。

## 2. 硬约束（评审通过标准）

1. **SMB 零回归**：更换数据流底座后，共享文件夹中转的功能与既有行为（配对、连接验证、设备枚举、命令、终端流、接管/交还、断线恢复、归档）不受影响，全量 `tests/run_all.py` 通过，尤其 `test_relay_*` 全部保持通过。
2. **本机自回环 TCP 双端验证**：不依赖真实双机，用 `127.0.0.1` 起主控 + 从机两个节点跑完整双端流程。
3. **本机自回环串口双端验证**：通过**虚拟串口对**（如 com0com 创建 `COM3 ↔ COM4`）在本机实现主控/从机各占一端，跑完整双端流程。

## 3. 现状与问题

### 3.1 载体抽象是半成品

[relay_carrier.py](../relay/relay_carrier.py) 蓝图声称「上层只依赖 `RelayCarrier` 接口，新增以太网直连时协议层、会话层、前端都不需要改动」。但实际只有链路探测走了 carrier：

| 职责 | 现状实现 | 是否走 carrier |
|---|---|---|
| 链路探测 / 状态 | `carrier.open()/status()` | ✅ 是 |
| 请求 / 结果 / 心跳 | `RelayQueue` 直接 `os.listdir`/`atomic_write_json`/`.jsonl` | ❌ 否 |
| 终端 / 日志流 | `StreamTail`/`StreamChannel` 直接文件 offset 读写 | ❌ 否 |
| 会话 / 控制日志 | `relay_session`/`relay_journal` 直接文件 / sqlite | ❌ 否 |

关键依据见 [relay_node.py](../relay/relay_node.py#L14-L16)：**链路语义走载体，分区路径语义走 `RelayQueue`（直接碰文件）**。

### 3.2 串口决定抽象必须降到「数据流」

串口只有字节流，没有目录、rename、文件等语义。任何「目录镜像 / 文件操作重放」方案（把共享目录在 TCP 上同步）都无法在串口上承载。因此唯一能同时容纳三种介质的抽象，是 `RelayCarrier` 已经声明但未被使用的两类语义：**命名消息槽 + 命名增量流**。

### 3.3 术语澄清

「串口」在本项目有两种含义，必须区分：

| 含义 | 现状 | 与本文关系 |
|---|---|---|
| 串口作为**受控设备**（串口终端） | 已有，走中转的 `serial-*` 流（`serial_stream.py`） | 不涉及 |
| 串口作为**中转载体**（两台电脑用串口互连） | 无 | 本文 `SerialCarrier` 新增 |

`SerialCarrier` 的串口是**中转专用、独占**，不复用串口终端的共享连接。

## 4. 核心抽象：数据流

载体向外只暴露两种数据形态，与介质无关：

1. **命名消息槽（slot + key → bytes）**：一条消息一个键，可靠、可枚举、可消费、可归档。用于 `requests` / `results` / `peers`（心跳）。
2. **命名增量流（name → 追加字节）**：单向追加，读端持游标增量读。用于终端与日志。

现有文件语义到数据流语义的映射：

| 现有文件语义 | 数据流语义 |
|---|---|
| `requests/<peer>/r-*.json` 一个请求一个文件 | 消息槽 `requests`，key = 请求文件名 |
| `results/<peer>/<reqId>.json` | 消息槽 `results`，key = reqId |
| `peers/<peerId>.json` 心跳 | 消息槽 `peers`，key = peerId |
| `streams/<peer>/<streamId>.out/.in/.meta` | 增量流 `streamId.out` / `streamId.in` / 消息 `streamId.meta` |
| `archive/<target>/transfers/<source>/<id>/upload.zip`·`download.zip` 文件传输 | 大块数据，当前共享目录整包 zip 交换，非消息槽/增量流；TCP 载体下改流式直传（见 §8.2） |
| `.from-<peer>.jsonl` / `.replies.jsonl` 通知 | **不进入抽象**（见 §9.4） |

## 5. 分层架构

```
L3 协议层    请求/结果/心跳/会话/日志  ← 只依赖 L2，不感知介质
L2 载体      RelayCarrier：命名消息槽 + 命名增量流
L1 帧协议    字节流 ↔ 帧（TCP 与串口共享；共享目录无此层）
L0 传输介质  文件系统 │ TCP 套接字 │ 串口
```

三种载体在 L1 的差异：

| 载体 | L1 帧协议 | 消息投递 | 流 |
|---|---|---|---|
| 共享文件夹 | 无（文件系统承载） | 目录枚举 + 独立文件 + jsonl 通知 | 文件 offset 追加 |
| TCP | 长度前缀分帧 | 帧按序到达（推送） | 接收缓冲 |
| 串口 | 定界 + CRC + 分片 + 重传 + 流控 | 帧按序到达（确认/重传） | 接收缓冲（低带宽） |

## 6. 载体接口契约（L2）

在 [relay_carrier.py](../relay/relay_carrier.py#L183-L250) 现有抽象基础上**补齐顺序与消费语义**，形成定稿契约：

```python
class RelayCarrier:
    kind: str
    def open(self) -> bool: ...
    def close(self) -> None: ...
    def is_open(self) -> bool: ...
    def status(self) -> dict: ...

    # 命名消息槽
    def put_message(self, slot, key, data) -> bool: ...
    def read_message(self, slot, key) -> Optional[bytes]: ...
    def list_keys(self, slot, prefix='', suffix='') -> list[str]: ...   # 有序
    def drop_message(self, slot, key) -> bool: ...
    def move_message(self, slot, key, target_slot) -> Optional[str]: ...

    # 命名增量流（游标由载体实例持有）
    def append_stream(self, name, data) -> bool: ...
    def read_stream(self, name, limit) -> tuple[bytes, bool]: ...       # (新字节, 是否重建)
    def reset_stream(self, name) -> None: ...
```

### 6.1 必须补齐的语义

1. **顺序**：`list_keys` 必须返回**有序**列表。共享目录按文件名字典序（现有 `make_req_filename` 定宽保证）；TCP/串口按帧到达序。协议层只依赖「有序」，不依赖具体排序来源。
2. **消费语义**：`read_message` + `drop_message` 组成「取出」；`move_message` 组成「归档」。协议层对这三者的调用组合必须等价于现有「读结果 + 归档」。
3. **幂等**：`key` 全局唯一标识一条消息；重复 `put` 同一 key 由实现保证不重复投递（共享目录靠原子写覆盖，TCP/串口靠 seq 去重）。
4. **分区解耦**：carrier 键名**不允许斜杠**（`_SAFE_SEGMENT_RE`），因此不承载 `<槽>/<peerId>/<键>` 三层路径。点对点单链路天然无分区，多从机 = 多个载体实例（§11）。

## 7. 帧协议层（L1，TCP 与串口共享）

帧承载两种数据：**消息槽操作**（`PUT/READ/LIST/DROP/MOVE` + slot + key + payload）与**流操作**（`APPEND/READ/RESET` + name + payload）。统一帧结构：

```
[帧头: type | slot/name | seq | length] [payload]
```

### 7.1 TCP

可靠有序字节流，只需**长度前缀分帧**（4 字节大端 length + 帧体）。连接即通道，TCP 自身保证顺序与不丢。

### 7.2 串口

裸字节流，需自实现可靠层：

1. **帧定界**：COBS 或 0x7E 转义（推荐 COBS，开销固定）。
2. **校验**：CRC16-CCITT 尾帧。
3. **分片重组**：单帧超过 `max_message_bytes`（spec 为 4 KiB）时按 seq 分片，收端重组。
4. **确认与重传**：滑动窗口 / 停等 ACK，超时重传，乱序去重。
5. **流控**：低带宽（默认 115200），终端流需节流与背压。

TCP 与串口共享同一套「帧编解码 + 分片 + seq」，只差「可靠性处理」——TCP 内建，串口自实现。这部分是独立、可单独测试的纯逻辑。

## 8. 三种载体实现

| 载体 | 实现要点 |
|---|---|
| `SharedFolderCarrier` | **保持现状**：文件系统落地消息槽与流，保留 SMB 负缓存规避、原子写、jsonl 通知等既有优化；新增「通过 L2 接口访问」的适配，不重写内部 |
| `TcpCarrier` | 主控 `listen`、从机 `connect`（仅局域网直连）；`sharedKey` 做 PSK 认证（HMAC 挑战应答）；断线自动重连；心跳保活 |
| `SerialCarrier` | `pyserial` 独占打开 COM；帧定界 + CRC + 分片 + 重传 + 流控；带宽受限，`throughput='low'` |

### 8.1 载体边界

`TcpCarrier` 仅支持局域网 / 可直接路由的直连，不负责 NAT 穿透与公网可达。公网场景由外部隧道（WireGuard / Tailscale / FRP）把对端映射为可达地址后复用本载体。载体不在协议层区分局域网与互联网，也不自建穿透或中转服务器。

### 8.2 文件传输的载体语义

文件传输（`file-transfer` / `file-transfer-cleanup`）**同样经过载体**，是数据形态特殊的一类：当前 `SharedFolderCarrier` 上是「打包 zip → 整包写入 `archive/<target>/transfers/<source>/<id>/` → 对端整包读 + 解包」（见 [relay_transfer.py](../relay/relay_transfer.py)），属于**大块数据 + 整包完成后才可见**的语义，不属于消息槽/增量流。

`TcpCarrier` 下可改为**流式直传**（边发边收），无需打包 zip、也无需等待整包落盘，延迟与磁盘占用均优于整包交换——这是 TCP 相对 SMB 在文件传输上的主要收益，也是载体抽象需要单独处理的一类数据形态。

## 9. 协议层改造与 SMB 零回归

### 9.1 改造映射

| 模块 | 现状 | 改为 |
|---|---|---|
| `RelayQueue`（[relay_protocol.py](../relay/relay_protocol.py#L345-L391)） | `os.listdir`/`atomic_write_json`/`.jsonl` | `put_message`/`list_keys`/`read_message`/`move_message` |
| `StreamTail`/`StreamWriter`/`StreamChannel`（[relay_stream.py](../relay/relay_stream.py)） | 文件 offset 读写 | `append_stream`/`read_stream`/`reset_stream` |
| `relay_session`（[relay_session.py](../relay/relay_session.py#L175-L217)） | `.out/.in/.meta` + zip 归档 | 流 + `move_message` 归档 |
| 心跳 `peers/` | 每 peer 一个文件 | 消息槽 `peers`（key = peerId） |

### 9.2 SMB 零回归策略（核心）

1. `SharedFolderCarrier` 的内部实现**逐字节保持现状**，只增加「实现 L2 接口」的适配层，文件布局不变。
2. 协议层改造后，用 §12 的**载体验证矩阵**证明：`shared-folder` 载体跑出的结果与改造前一致（同一批 `test_relay_*` 断言不变）。
3. 全量 `tests/run_all.py` 作为守护；任何 shared-folder 回归即视为方案失败。

### 9.3 顺序与幂等的等价性

共享目录靠「文件名字典序 + 独立文件」保证顺序与幂等；TCP/串口靠「帧到达序 + seq」。协议层抽象为「有序消息槽」后，两者行为一致。这是 SMB 零回归的语义基础。

### 9.4 jsonl 快速通道的去留

`.from-<peer>.jsonl` / `.replies.jsonl` 是**共享目录/SMB 的性能优化**（避免海量小文件的 listdir 负缓存）。它是 `SharedFolderCarrier` 的**内部实现细节**，不进 L2 抽象。TCP/串口天然推送（`push_stream=True`），不需要它；共享目录保留它。协议层通过 L2 接口调用，感知不到这层差异。

## 10. 会话与日志按载体分化

`relay_journal`（[relay_journal.py](../relay/relay_journal.py)）是「不可靠链路的持久收件箱」——控制面消息落盘、断线不丢。它的启用与否应由载体能力决定：

| 载体 | journal 策略 |
|---|---|
| 共享文件夹 | 保留（现状） |
| 串口 | 保留（会丢帧、会断） |
| TCP | 可绕过（可靠 + ACK，`push_stream=True`） |

这是数据流抽象带来的自然分化点，需在改造时显式决策。

## 11. p2p 拓扑与多从机

共享目录是**总线**（多方共享一个目录，靠分区隔离多从机）；TCP/串口是**点对点**（一条链路一个从机）。因此：

- 单链路**无分区**，消除了「carrier 键名不允许斜杠」与「三层路径」的矛盾。
- 多从机 = **多个载体实例**。[relay_node.py](../relay/relay_node.py) 中单 `self.carrier` 需改为「按从机持有载体集合」，`_peer_roots` 路由逻辑随之调整。

这是除 L2 重构外的第二处实质改动，需重点回归既有路由/配对测试。

## 12. 测试方案（本机自回环）

### 12.1 总策略

**载体验证矩阵**：同一套「主控 + 从机」端到端协议场景，参数化跑 `shared-folder` / `tcp` / `serial` 三种载体，证明协议层与介质解耦。共享目录载体结果与改造前一致，即 SMB 零回归。

### 12.2 测试分层

| 层 | 内容 | 载体 |
|---|---|---|
| 帧协议单测 | 分帧 / 半包 / 粘包 / CRC 错帧 / 分片重组 / seq 续传 / 超时重传 | tcp + serial |
| 载体契约单测 | `put/read/list/drop/move_message`、`append/read/reset_stream` 及顺序/幂等语义 | 三种全跑 |
| 协议层集成（本机回环） | 配对 → 连接验证 → 设备枚举 → 命令 → 终端流 → 接管/交还 → 断线重连 | 三态同断言 |
| 双端真实验证 | 双机 / 双串口对连 | tcp + serial |
| SMB 回归 | `run_all.py` 全量 | shared-folder |

### 12.3 本机自回环 TCP 双端

抽象工厂 `make_relay_pair(kind)`：同一进程内起两个 `RelayNode`（一个主控、一个从机），TCP 用 `127.0.0.1` 回环（主控 listen、从机 connect）。复用现有 `test_relay_*` 的「临时目录当共享根」思路，把「共享根」换成「回环连接」即可。

### 12.4 本机自回环串口双端（虚拟串口对）

1. **虚拟串口对**：用 com0com（开源）创建成对串口（如 `COM3 ↔ COM4`），主控开 `COM3`、从机开 `COM4`，数据流在虚拟层闭环。
2. **环境检测**：测试入口检测虚拟串口对是否可用；不可用时按现有 `ENV-BLOCKED` 机制标记（对齐 `run_all.py` 里米家 DPAPI 预检的做法），不当作失败。
3. **故障注入**：用可编程的「虚拟串口包装层」注入丢帧、错帧、乱序、延迟，验证可靠性层，而不是依赖真实线缆的偶然故障。

### 12.5 测试入口

新增测试组进 `tests/run_all.py`（如 `Relay TCP Carrier`、`Relay Serial Carrier`）；虚拟串口对不可用时 `ENV-BLOCKED`。共享目录的既有 26 组 `test_relay_*` 保持登记、保持通过。

## 13. 分阶段落地

| 阶段 | 内容 | 验证 |
|---|---|---|
| 0 | 冻结 L2 接口契约（本文 §6）+ 设计评审通过 | 评审 |
| 1 | 帧协议层（TCP + 串口共享底座） | 帧协议单测 |
| 2 | 协议层重构走 L2，`SharedFolderCarrier` 保持现状 | 三态矩阵 + SMB 回归 |
| 3 | `TcpCarrier` + 连接管理 / PSK 认证 / 重连 | 本机回环 TCP 双端 |
| 4 | `SerialCarrier`（定界/CRC/分片/重传/流控） | 虚拟串口对双端 + 故障注入 |
| 5 | `relay_journal` 按载体分化 + 前端设置表单 | UI 断言 + 回归 |
| 6 | 双机 / 双串口真实验证 + 全量回归 | `run_all.py` |

阶段 2 是风险最高的重构，必须先于阶段 3/4，且每次改动都以「shared-folder 结果不变」为门槛。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 协议层重构破坏 SMB 行为 | 高 | §9.2 逐字节保持 + 三态矩阵 + 全量回归 |
| 帧协议 / 分片重传的隐蔽 bug | 高 | 阶段 1 单测用「操作序列 fuzz + 随机丢帧/错帧」 |
| 多从机 = 多载体，路由/配对回归 | 中高 | §11 重点回归 `_peer_roots` 路由与配对测试 |
| 串口带宽受限导致终端卡顿 | 中 | 流控 + 背压，`throughput='low'` 明确降级 |
| `relay_journal` 分化引入载体差异 | 中 | §10 显式决策，按载体能力启用，避免隐性分支 |
