# DevMux 3.2.1 发布流程

> 内部流程文档，不随发布包分发。用户可见的版本变化写在 `发布说明.md`，随包文档清单由 `doc_links.DOCUMENTS` 定义。

开发分支先构建新包，再运行专项测试；合入主线后重新构建主线目标包，再按 `python tests/run_all.py` 顺序全量验证，全部通过后才能公开发布。失败、跳过、环境阻塞均不能算通过。每次提交前必须展示完整 message 并取得明确确认。

## 构建

使用 64 位 Windows、Python 3.10+（实际验证环境见构建证据）、WebView2 Runtime，安装 `pip install -r requirements-build.txt`。准备完整 Android platform-tools，设置 `ADB_BUNDLE_DIR` 指向含 adb.exe、fastboot.exe、mke2fs.exe、mke2fs.conf 及配套 DLL 的目录；不得只复制 adb.exe。源码运行还可通过 ADB_PATH 指定 ADB。

`python release_bundle.py` 构建候选包，同时记录未提交状态和每个源码文件摘要。候选包仅供验证。正式发布使用 `python release_bundle.py --release`，要求干净工作树、HEAD 与 `v3.2.1` tag 完整提交一致。先获准提交及合入，再创建对应 tag，执行正式构建和主线全量测试；测试不得改写待发布产物。

正式版 `build.spec` 与调试版 `build_debug.spec` 均调用 `release_plugins.py`，四个官方包在 dist/plugin/，命名为插件ID-插件版本.dmp；调试版用 `python -m PyInstaller build_debug.spec --clean --noconfirm`，不混入正式 ZIP。

发版时本版真实变化写进 `发布说明.md`，不能只替换版本号：`使用说明.md` 首行版本要更新，`发布说明.md` 的 `# DevMux <版本>` 小节须逐条写明本版改动（≥200 字、≥3 条），`Agent接入说明.md` 与说明中的源码包名同步为新版本。`使用说明.md` 是用户手册，只写功能与操作，出现版本化小节（如 `### 3.2.0 …`、`（v2.3.1）`）会被判越界。`tests/test_docs_version.py` 会校验这些项，空壳小节、残留旧包名或手册里夹带变更叙述都会导致全量失败。

构建结束时会自动同步本地部署目录：`dist/` 按 `DOCUMENTS` 白名单**整份铺开**（含 `docs/` 子树），内容相同则不重写，并清掉上一版残留的随包文档。该目录是 `.gitignore` 的本机运行位置，也是双击 `DevMux.exe` 的地方，因此同步后它就是一份自洽的交付集：可执行程序、`plugin/` 四个官方包、随包文档互相引用都能解析。`doc_links.py` 会在同步后校验链接，指向包外的链接直接判失败；不触碰 `devmux-data` 与 `plugin`。若发现 `dist/` 里还有旧版本文档，说明该次构建未走 `release_bundle.py`。

## 交付清单

每次输出使用独立 `dist/releases/版本-UTC时间/`，保留历史文件及运行数据。Windows ZIP 只从白名单整理：DevMux.exe、plugin/ 中 usb-relay、db-flash、mijia、ebpf 四包、README、使用说明、Agent 接入说明、发布说明、许可、串口说明、插件开发说明、来源记录、BUILD-INFO 和内部 SHA256SUMS。白名单即 `doc_links.DOCUMENTS`，`tests/test_docs_version.py` 会校验它的每一项确实存在、链接闭合；`docs/internal/` 下的设计、需求与流程文档不进包。禁止打入 devmux-data、配置、日志、凭据及已安装插件数据。

同一个 Release 上传 Windows ZIP、对应源码 ZIP、BUILD-INFO.json、build.log、build-environment.txt、SHA256SUMS.txt、latest.json，以及 plugin/ 下 usb-relay、db-flash、mijia、ebpf 四个 .dmp（插件独立升级的下载源）。BUILD-INFO 记录 tag、完整提交、是否 dirty、构建命令、Python/系统、依赖清单与日志摘要、源码文件摘要；校验清单包含外部交付文件摘要，ZIP 内清单单独校验内容。候选证据明确标为 candidate，不能伪装正式版本。版本号或校验摘要本身不能证明二进制来源，当前证据是本地构建追溯记录，不声称独立可复现或签名认证。

## 验收与发布

专项测试：`python -m unittest tests.test_agent_plugins tests.test_release_bundle`，以及 `python -B tests/test_app_paths.py`、`python -B tests/test_plugin_runtime.py`、`python -B tests/test_plugin_frozen.py`、`python -B tests/test_agent.py`、`python -B -m tests.test_agent_extensions`。新增专项用例也纳入 run_all.py。

主线全量测试前先构建目标包。米家 DPAPI 受限失败时，保留原结果，在获授权的当前用户沙箱外重跑同一测试，不操作用户凭据。全部结果如实记录，未完成不得发布。

正式发布执行 `python release_publish.py`：校验交付目录与 `v<版本>` tag 指向当前 HEAD，双远端（origin、gitee）推送 master 与 tag，创建 GitHub Release 并上传交付目录与 `latest.json` 列出的全部资产（Windows ZIP、源码 ZIP、latest.json、BUILD-INFO、build.log、build-environment、SHA256SUMS、四个官方 .dmp），最后用 `gh api` 确认每个资产都是 `uploaded`。资产清单由产物决定并由脚本校验，**不需要人工逐个核对**；重复执行会补齐缺失资产。仅当连接器具备等价的创建/上传能力时改用 MCP。

公开后从 Releases 下载 Windows ZIP 与校验清单并解压，核对版本、四包、说明、SHA-256 和完整提交，普通桌面启动并连接 MCP，使用隔离测试插件验证安装、启用、查询、停用。不得以无窗口启动代替桌面启动，也不得用打包或模拟测试冒充首次使用验收；受环境限制时明确列出未验证项。

## 更新清单

`latest.json` 是已安装客户端唯一解析的清单，随每次构建生成到交付目录，并作为独立发布资产上传（不打进 ZIP）。`version`/`tag`/`status` 说明来源，`assets.windows` 记录本机 ZIP 的文件名、大小、SHA-256 与下载地址（打包后计算，不手工填写），`plugins` 段由 `release_plugins.catalog()` 从实际 `.dmp` 产物读取版本、大小与 SHA-256。四个 `.dmp` 同时作为独立 Release 资产上传：必须上传 `dist/releases/版本-UTC时间/delivery/plugin/` 下的产物（`plugins[].sha256` 从这批文件计算），不能用 `dist/plugin/` 的另一次打包产物——`.dmp` 打包会把 mtime 写进 zip，两次打包摘要不一致。

客户端只接受 `status: release` 的清单：候选包的清单即使流出也不会触发升级。下载地址不写死在客户端——发布时用 `DEVMUX_DOWNLOAD_MIRRORS` 注入镜像模板（`{tag}`、`{name}` 占位，逗号分隔），生成进 `urls` 数组按顺序回退。需要强制旧版升级时，用 `DEVMUX_MIN_SUPPORTED_VERSION` 注入下限；不注入就不写该字段，客户端不会凭空要求升级。

**发布前必须确认每个 `.dmp` 的版本号与该插件本次改动一致**：客户端只按版本号判断新旧，改了内容不升版本等于没发布；反过来只改主程序时不要动插件版本，用户不会被提示升级插件。

## 主程序升级流程（客户端侧）

升级链路是「检测 → 下载校验 → 解压暂存 → 退出替换 → 重启」，实现分布在 `app_update.py`（前四步）与 `update_apply.py`（替换）：

- 运行数据在 `devmux-data/`：`update-state.json` 记检测结果与暂存信息，`update-restart.json` 是退出时的替换待办，`updates/<版本>/` 放下载包与 `staged/` 解压结果，`update-result.json` 由替换进程写入、新版启动后读一次。
- 暂存只解压白名单条目（`DevMux.exe`、`BUILD-INFO.json`、`SHA256SUMS.txt`、`plugin/*.dmp`）；包里的文档按设计忽略，非法路径与符号链接直接拒绝整包。
- 替换由「自身副本 + `--apply-update`」完成：主进程收尾时把 exe 复制到临时目录启动，等目标 exe 可独占打开后改名旧版、落新文件、启动新版。全流程不要求管理员权限，仅安装目录不可写时失败并保留已下载的包。
- 卸载/回滚：旧版保留为 `DevMux.exe.old-<时间戳>`，7 天后自动清理；替换失败会立即改名还原，`update-result.json` 记录原因。
- 升级不影响已安装插件与用户数据：只有 `DevMux.exe` 与 `plugin/*.dmp` 会被覆盖，`devmux-data/` 不在替换范围内。
