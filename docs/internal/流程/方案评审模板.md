# 方案评审模板（需求 → 设计 → 验证 → 交付）

> 内部文档，不随发布包分发。用途：**任何非琐碎功能或架构改动，在写第一行代码前**用本模板出方案并评审。
>
> 目的：把需求、验收标准、测试映射、完成定义、回滚方案在评审阶段定死，避免「开发到一半才发现没定义」。
>
> 登记：`docs/文档索引.md`。小改动可只填第 0 节并过第 6 节门禁；功能/架构改动填完整六节。

## 文件布局（评审产物不入库）

每个任务一个目录，六张卡各一个文件：

```
docs/runs/<yyyyMMdd>-<任务简称>/
    0-一页结论.md      # §0 一页结论 + §6 评审门禁
    1-需求卡.md        # §1
    2-方案卡.md        # §2
    3-验证卡.md        # §3
    4-交付卡.md        # §4
    5-决策记录.md      # §5
```

- `docs/runs/` 已在 `.gitignore`，**不提交、不登记文档索引、不进发布包**。
- 同一任务的设计结论仍回写到权威设计文档（如 `docs/internal/跨机中转载体设计.md`）；`runs/` 只是过程记录与评审凭据。
- 目录名用日期+任务简称，避免不同任务互相覆盖。

## 0. 一页结论（评审先看这页）

| 项 | 内容 |
|---|---|
| 需求编号 | `REQ-xxx`（一个编号一条可验收需求，不与实现绑定） |
| 一句话目标 | 用户能做什么，而不是代码改了什么 |
| 明确不做 | 列出本次**不**覆盖的场景，防止范围蔓延 |
| 验收标准 | AC1、AC2……每条都是可判真假的句子 |
| 最大风险 | 最可能让方案失败的一件事 |
| 可回滚性 | 出错时怎么退回（开关/保留旧路径/数据兼容） |
| 方案状态 | 评审稿 / 已定稿（定稿才能开工） |

## 1. 需求卡

- **背景与问题**：现在哪里不行，谁在什么场景下受影响，有无现场证据（日志、复现步骤）。
- **用户场景**：按「角色 + 触发 + 期望结果」写，一条场景对应一个 AC。
- **范围**：本次覆盖的功能边界。
- **非目标**：本次明确不做的事，逐条写，不允许留空。
- **依赖与约束**：硬件、操作系统、网络、外部服务、版本兼容、性能上限。

> 反例：只写「支持 TCP 直连」，不写「是否包含公网、是否包含多从机、是否包含 UI 配置」——开发到一半必然返工。

## 2. 方案卡

- **现状与约束**：以代码事实为准，带文件路径/行号；写清哪些现有行为不能变。
- **备选方案与取舍**：至少两个方案，逐个写优点、代价、被否掉的具体原因。
- **接口契约**：函数签名、消息/帧格式、文件布局、错误语义（抛异常还是返回 False）。
- **数据与状态**：状态机、持久化位置、并发模型、生命周期（谁创建、谁关闭）。
- **兼容性与回滚**：旧数据/旧配置/旧版本客户端如何处理；回滚步骤是否可执行。
- **安全边界**：认证、授权、暴露面、失败时的默认行为（fail-closed/fail-open）。

## 3. 验证卡

**测试矩阵是评审必填项，不是开发完再补。**

| AC 编号 | 用例/断言 | 层级（单测/集成/端到端/人工） | 测试入口 | 环境依赖 |
|---|---|---|---|---|
| AC1 | …… | 单测 | `tests/test_xxx.py` | 无 |
| AC2 | …… | 端到端 | `tests/test_xxx_e2e.py` | 需真实设备/第二台机器 |

- **环境依赖与阻塞**：需要真实硬件、第二台机器、特定系统版本的用例，提前声明 `ENV-BLOCKED` 判定口径。
- **不验证什么**：明确免责范围，避免「没测=没做」和「说测了其实没测」两种误解。
- **回归范围**：本次可能影响的既有测试组，逐条列出（不是「跑全量」一句话）。

## 4. 交付卡（分阶段，每阶段有可判真假的 DoD）

| 阶段 | 交付物 | DoD（逐项可勾选） | 阻塞点 |
|---|---|---|---|
| 1 | …… | 代码 + 单测 + 相关回归组 + 文档回写 | 无 |
| 2 | …… | 同上 + 端到端用例 + 兼容性验证 | 依赖阶段 1 定稿 |

每个阶段的 DoD 固定包含六项：

1. 代码实现（不含占位/TODO 分支）
2. 单元测试与断言清单
3. 受影响的回归测试组（列出组名与结果）
4. 文档回写（权威文档路径 + 引用点）
5. 兼容性/回滚验证
6. 提交 message 草案

另需写明：**发布影响**（是否升主程序版本、是否升插件版本、是否要写发布说明、是否影响随包文档）。

## 5. 决策记录（ADR-lite）

| 编号 | 决策 | 备选 | 结论 | 理由 | 日期 | 影响文件 |
|---|---|---|---|---|---|---|
| ADR-1 | …… | A/B | 选 A | …… | yyyy-mm-dd | `relay/xxx.py` |

规则：方案中每个「待评审决策点」在定稿时必须落到本表，写明结论与理由；不允许把未决项带进开发。

## 6. 评审门禁（全部满足才能开工）

- [ ] 每条 AC 都能在验证卡里找到对应用例，且用例能判真假
- [ ] 所有「待评审决策点」已关闭，或明确写入「非目标」并说明何时再做
- [ ] 没有「先写着、以后再定」的接口、数据结构或文件布局
- [ ] 兼容性与回滚方案可执行（不是「注意兼容」这种描述）
- [ ] 每个阶段 DoD 可判真假（拒绝「完成开发」这类描述）
- [ ] 权威文档已确定并登记 `docs/文档索引.md`
- [ ] 未决事项都有负责人与截止阶段（不允许无主）

**评审结论**：通过 / 有条件通过（列出条件与关闭时间）/ 打回。

## 7. 本项目已踩过的点（模板的由来）

- **TCP 载体方案**：方案只写了测试矩阵，没写 AC 编号与用例映射；阶段 1 完成时才发现「完整功能」还缺协议层接线与 UI 配置——这些本应在「非目标」与阶段 DoD 中写明，评审时即可暴露。
- **串口载体反复**：先定「保留串口」，开发中才确认「完全去掉」，导致文档与代码各改一遍。若有「明确不做」清单且评审时确认，第一次定稿就会收敛。
- **文档定稿时机**：方案文档长期停留在「评审稿」，代码却已开工；门禁要求「方案已定稿」才能进开发，可避免文档与实现脱节。
