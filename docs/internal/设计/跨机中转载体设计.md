# 跨机中转载体设计（数据流底座）

> 内部设计文档，不随发布包分发。本文是**长期架构契约**（2026-11-17 已定稿）；本次任务的分阶段计划、验证结果与决策记录见 `docs/runs/20261117-跨机中转TCP载体/`（本地、不入库）。
>
> 与 [跨机中转设计.md](/docs/internal/设计/跨机中转设计.md) 的分工：那一份讲**交互约定、状态机、心跳与接管**（控制面与业务语义）；本份讲**传输底座**——把「链路」从单一 SMB 共享目录，抽象成可插拔的数据流载体，使以太网直连复用同一套协议层。

## 0. 结论摘要

1. 现有 `relay_carrier.py` 的 `RelayCarrier` 抽象是**半成品**：协议层（`RelayQueue`、`StreamChannel`、`relay_session`、`relay_journal`、心跳）全部直接操作文件系统路径，只有「链路探测/状态」真正走了 carrier。
2. TCP 直连是字节流（socket），没有文件系统语义；现有协议层深度绑定文件系统路径，直接加 `TcpCarrier` 无法复用。因此载体抽象必须下沉到**数据流**级别——即 `RelayCarrier` 已定义的「命名消息槽 + 命名增量流」两类语义，作为 SMB / TCP 两种介质的共同抽象。
3. 方案核心是**把协议层从文件系统路径改为走载体数据流接口**，`SharedFolderCarrier` 保持现状作为该接口的文件系统落地；新增 `TcpCarrier` 复用同一套协议层。
4. 通过**载体验证矩阵**（shared-folder × tcp 两态跑同一批协议场景）保证协议层与介质解耦，并以**本机自回环**（127.0.0.1）完成 TCP 双端验证，SMB 全量回归守护零退化。

## 1. 背景与目标

- **目标**：把跨机中转的传输底座做成可插拔，新增「以太网直连（TCP）」载体；两种载体共用同一套协议层与业务语义。
- **非目标**：不改变配对、心跳、接管、命令白名单等**业务语义**（见 [跨机中转设计.md](/docs/internal/设计/跨机中转设计.md)）；不引入整体框架替换；不改变共享文件夹的既有文件布局与行为。

## 2. 硬约束（评审通过标准）

1. **SMB 零回归**：更换数据流底座后，共享文件夹中转的功能与既有行为（配对、连接验证、设备枚举、命令、终端流、接管/交还、断线恢复、归档）不受影响，全量 `tests/run_all.py` 通过，尤其 `test_relay_*` 全部保持通过。
2. **本机自回环 TCP 双端验证**：不依赖真实双机，用 `127.0.0.1` 起主控 + 从机两个节点跑完整双端流程。

## 3. 现状与问题

### 3.1 载体抽象是半成品

[relay_carrier.py](/relay/relay_carrier.py) 蓝图声称「上层只依赖 `RelayCarrier` 接口，新增以太网直连时协议层、会话层、前端都不需要改动」。但实际只有链路探测走了 carrier：

| 职责 | 现状实现 | 是否走 carrier |
|---|---|---|
| 链路探测 / 状态 | `carrier.open()/status()` | ✅ 是 |
| 请求 / 结果 / 心跳 | `RelayQueue` 直接 `os.listdir`/`atomic_write_json`/`.jsonl` | ❌ 否 |
| 终端 / 日志流 | `StreamTail`/`StreamChannel` 直接文件 offset 读写 | ❌ 否 |
| 会话 / 控制日志 | `relay_session`/`relay_journal` 直接文件 / sqlite | ❌ 否 |

关键依据见 [relay_node.py](/relay/relay_node.py#L14-L16)：**链路语义走载体，分区路径语义走 `RelayQueue`（直接碰文件）**。

### 3.2 数据流抽象的必要性

TCP 直连是字节流（socket），没有目录、rename、文件等语义。现有协议层深度绑定文件系统路径（`os.listdir`、文件 offset、`rename`），若只加一个 `TcpCarrier` 而不做抽象，`RelayQueue` 仍会读写本地文件路径，TCP 接不上协议数据。因此必须把协议层从「文件系统路径语义」下沉到「数据流语义」——即 `RelayCarrier` 已声明但未被使用的两类语义：**命名消息槽 + 命名增量流**。这是 SMB（文件系统）与 TCP（字节流）的共同抽象，也为未来扩展其他介质保留空间。

## 4. 核心抽象：数据流

载体向外只暴露两种数据形态，与介质无关：

1. **命名消息槽（slot + key → bytes）**：一条消息一个键，可靠、可枚举、可消费、可归档。用于 `requests` / `results` / `peers`（心跳）。
2. **命名增量流（name → 追加字节）**：单向追加，读端持游标增量读。用于终端与日志。

现有文件语义到数据流语义的映射：

| 现有文件语义 | 数据流语义 |
|---|---|
| `requests/<peer>/r-*.json` 一个请求一个文件 | 消息槽 `requests`，key = 请求文件名 |
| `results/<peer>/<reqId>.json` | 消息槽 `results`，key = reqId |
| `peers/<peerId>.json` 心跳 | 消息槽 `peers`，key = peerId |
| `streams/<peer>/<streamId>.out/.in/.meta` | 增量流 `streamId.out` / `streamId.in` / 消息 `streamId.meta` |
| `archive/<target>/transfers/<source>/<id>/upload.zip`·`download.zip` 文件传输 | 复用「增量流 + 元数据消息槽」承载：数据流 `transfer-<id>.bin` + 元数据消息 `transfer-meta`（见 §6.2） |
| `.from-<peer>.jsonl` / `.replies.jsonl` 通知 | **不进入抽象**（见 §9.4） |

## 5. 分层架构

```
L3 协议层    请求/结果/心跳/会话/日志  ← 只依赖 L2，不感知介质
L2 载体      RelayCarrier：命名消息槽 + 命名增量流
L1 帧协议    字节流 ↔ 帧（仅 TCP；共享目录无此层）
L0 传输介质  文件系统 │ TCP 套接字
```

两种载体在 L1 的差异：

| 载体 | L1 帧协议 | 消息投递 | 流 |
|---|---|---|---|
| 共享文件夹 | 无（文件系统承载） | 目录枚举 + 独立文件 + jsonl 通知 | 文件 offset 追加 |
| TCP | 长度前缀分帧 | 帧按序到达（推送） | 接收缓冲 |

## 6. 载体接口契约（L2）

在 [relay_carrier.py](/relay/relay_carrier.py#L183-L250) 现有抽象基础上**补齐顺序与消费语义**，形成定稿契约：

```python
class RelayCarrier:
    kind: str
    def open(self) -> bool: ...
    def close(self) -> None: ...
    def is_open(self) -> bool: ...
    def status(self) -> dict: ...

    # 命名消息槽
    def put_message(self, slot, key, data) -> bool: ...
    def read_message(self, slot, key) -> Optional[bytes]: ...
    def list_keys(self, slot, prefix='', suffix='') -> list[str]: ...   # 有序
    def drop_message(self, slot, key) -> bool: ...
    def move_message(self, slot, key, target_slot) -> Optional[str]: ...

    # 命名增量流（游标由载体实例持有）
    def append_stream(self, name, data) -> bool: ...
    def read_stream(self, name, limit) -> tuple[bytes, bool]: ...       # (新字节, 是否重建)
    def reset_stream(self, name) -> None: ...
```

### 6.1 必须补齐的语义

1. **顺序**：`list_keys` 必须返回**有序**列表。共享目录按文件名字典序（现有 `make_req_filename` 定宽保证）；TCP 按帧到达序。协议层只依赖「有序」，不依赖具体排序来源。
2. **消费语义**：`read_message` + `drop_message` 组成「取出」；`move_message` 组成「归档」。协议层对这三者的调用组合必须等价于现有「读结果 + 归档」。
3. **幂等**：`key` 全局唯一标识一条消息；重复 `put` 同一 key 由实现保证不重复投递（共享目录靠原子写覆盖，TCP 靠 seq 去重）。
4. **分区解耦**：carrier 键名**不允许斜杠**（`_SAFE_SEGMENT_RE`），因此不承载 `<槽>/<peerId>/<键>` 三层路径。点对点单链路天然无分区，多从机 = 多个载体实例（§11）。

### 6.2 文件传输的载体语义（复用增量流，已定：选项 A）

文件传输**不新增第三种接口形态**，复用已有「消息槽 + 增量流」两种形态的组合：

1. **传输数据** = 命名增量流 `transfer-<id>.bin`：分块 `append_stream` 发送、`read_stream` 增量接收。游标天然支持断点续传（记录已确认字节数即可续传）。
2. **传输元数据** = 消息槽 `transfer-meta`，key = `<id>.meta`：源/目标/路径/SHA256/块数/已确认字节/完成标志。先写「进行中」，数据流收齐且校验通过后改「完成」。
3. **完成可见性（不变量，沿用 SMB）**：目标端**整包完成前不可见**。数据先落临时文件，收到「完成」元数据后原子 `rename` 为最终路径——等价于 [relay_transfer.py](/relay/relay_transfer.py#L54-L60) 的 `.partial` → rename。TCP 流式直传也不得直接写目标文件。

两种载体落地方式：

| 载体 | 数据流落地 | 元数据落地 |
|---|---|---|
| 共享文件夹 | 增量流落地为 zip 文件（保持现状整包交换） | 消息槽落地为 `.meta` 文件 |
| TCP | 流式直传（边发边收，无 zip） | 帧消息 |

## 7. 帧协议层（L1，TCP）

TCP 是可靠有序字节流，只需**长度前缀分帧**（4 字节大端 length + 帧体）。帧承载两种数据：

- **消息槽操作**：`PUT/READ/LIST/DROP/MOVE` + slot + key + payload。
- **流操作**：`APPEND/READ/RESET` + name + payload。

统一帧结构：

```
[帧头: type | slot/name | seq | length] [payload]
```

连接即通道，TCP 自身保证顺序与不丢；`seq` 用于消息幂等去重。这部分是独立、可单独测试的纯逻辑。

## 8. 两种载体实现

| 载体 | 实现要点 |
|---|---|
| `SharedFolderCarrier` | **保持现状**：文件系统落地消息槽与流，保留 SMB 负缓存规避、原子写、jsonl 通知等既有优化；新增「通过 L2 接口访问」的适配，不重写内部 |
| `TcpCarrier` | 主控 `listen`、从机 `connect`（仅局域网直连）；`sharedKey` 做 PSK 认证（HMAC 挑战应答）；断线自动重连；心跳保活 |

### 8.1 载体边界

`TcpCarrier` 仅支持局域网 / 可直接路由的直连，不负责 NAT 穿透与公网可达。公网场景由外部隧道（WireGuard / Tailscale / FRP）把对端映射为可达地址后复用本载体。载体不在协议层区分局域网与互联网，也不自建穿透或中转服务器。

- **发现方向**：主控 `listen`、从机 `connect`（拨出）。TCP 没有「同一目录」的自动发现，从机仍需配置主控地址后拨出，主控侧交互流程不变（与共享目录「从机等待、主控确认」一致，见 [跨机中转设计.md](/docs/internal/设计/跨机中转设计.md)）。
- **安全边界**：共享目录靠 ACL + 连接代次防重放，本机配对记录不是密码认证；TCP 端口对外暴露，`sharedKey` 必须升级为**真实认证**（HMAC 挑战应答，未认证连接拒绝接收任何帧）。监听默认绑定指定网卡，不绑 `0.0.0.0`，缩小暴露面。

### 8.2 文件传输的载体语义

文件传输（`file-transfer` / `file-transfer-cleanup`）**同样经过载体**，落地方式见 §6.2：复用「增量流 `transfer-<id>.bin` + 元数据消息槽 `transfer-meta`」。

- 共享文件夹载体保持现状（整包 zip 交换），`transfer-<id>.bin` 流落地为 `upload.zip`/`download.zip` 文件，`transfer-meta` 落地为 `.meta` 文件——文件布局不变，SMB 零回归。
- TCP 载体改为**流式直传**（边发边收），无需打包 zip、无需等待整包落盘，延迟与磁盘占用优于整包交换——这是 TCP 相对 SMB 在文件传输上的主要收益。
- 无论哪种载体，**目标端整包完成前不可见**的不变量保持一致（临时文件 + 完成时原子 rename）。

## 9. 协议层改造与 SMB 零回归

### 9.1 改造映射

| 模块 | 现状 | 改为 |
|---|---|---|
| `RelayQueue`（[relay_protocol.py](/relay/relay_protocol.py#L345-L391)） | `os.listdir`/`atomic_write_json`/`.jsonl` | `put_message`/`list_keys`/`read_message`/`move_message` |
| `StreamTail`/`StreamWriter`/`StreamChannel`（[relay_stream.py](/relay/relay_stream.py)） | 文件 offset 读写 | `append_stream`/`read_stream`/`reset_stream` |
| `relay_session`（[relay_session.py](/relay/relay_session.py#L175-L217)） | `.out/.in/.meta` + zip 归档 | 流 + `move_message` 归档 |
| 心跳 `peers/` | 每 peer 一个文件 | 消息槽 `peers`（key = peerId） |

### 9.2 SMB 零回归策略（核心）

1. `SharedFolderCarrier` 的内部实现**逐字节保持现状**，只增加「实现 L2 接口」的适配层，文件布局不变。
2. 协议层改造后，用 §12 的**载体验证矩阵**证明：`shared-folder` 载体跑出的结果与改造前一致（同一批 `test_relay_*` 断言不变）。
3. 全量 `tests/run_all.py` 作为守护；任何 shared-folder 回归即视为方案失败。

### 9.3 顺序与幂等的等价性

共享目录靠「文件名字典序 + 独立文件」保证顺序与幂等；TCP 靠「帧到达序 + seq」。协议层抽象为「有序消息槽」后，两者行为一致。这是 SMB 零回归的语义基础。

### 9.4 jsonl 快速通道的去留

`.from-<peer>.jsonl` / `.replies.jsonl` 是**共享目录/SMB 的性能优化**（避免海量小文件的 listdir 负缓存）。它是 `SharedFolderCarrier` 的**内部实现细节**，不进 L2 抽象。TCP 天然推送（`push_stream=True`），不需要它；共享目录保留它。协议层通过 L2 接口调用，感知不到这层差异。

## 10. 会话与日志按载体分化

`relay_journal`（[relay_journal.py](/relay/relay_journal.py)）是「不可靠链路的持久收件箱」——控制面消息落盘、断线不丢。它的启用与否应由载体能力决定：

| 载体 | journal 策略 |
|---|---|
| 共享文件夹 | 保留（现状） |
| TCP | 可绕过（可靠 + ACK，`push_stream=True`） |

这是数据流抽象带来的自然分化点，需在改造时显式决策。

## 11. p2p 拓扑与多从机

共享目录是**总线**（多方共享一个目录，靠分区隔离多从机）；TCP 是**点对点**（一条链路一个从机）。因此：

- 单链路**无分区**，消除了「carrier 键名不允许斜杠」与「三层路径」的矛盾。
- 多从机 = **多个载体实例**。[relay_node.py](/relay/relay_node.py) 中单 `self.carrier` 需改为「按从机持有载体集合」，`_peer_roots` 路由逻辑随之调整。

这是除 L2 重构外的第二处实质改动，需重点回归既有路由/配对测试。

## 12. 测试方案（本机自回环）

### 12.1 总策略

**载体验证矩阵**：同一套「主控 + 从机」端到端协议场景，参数化跑 `shared-folder` / `tcp` 两种载体，证明协议层与介质解耦。共享目录载体结果与改造前一致，即 SMB 零回归。

### 12.2 测试分层

| 层 | 内容 | 载体 |
|---|---|---|
| 帧协议单测 | 分帧 / 半包 / 粘包 / seq 幂等去重 / 长度字段越界 | tcp |
| 载体契约单测 | `put/read/list/drop/move_message`、`append/read/reset_stream` 及顺序/幂等语义 | 两种全跑 |
| 协议层集成（本机回环） | 配对 → 连接验证 → 设备枚举 → 命令 → 终端流 → 接管/交还 → 断线重连 | 两态同断言 |
| 双端真实验证 | 双机 | tcp |
| SMB 回归 | `run_all.py` 全量 | shared-folder |

### 12.3 本机自回环 TCP 双端

抽象工厂 `make_relay_pair(kind)`：同一进程内起两个 `RelayNode`（一个主控、一个从机），TCP 用 `127.0.0.1` 回环（主控 listen、从机 connect）。复用现有 `test_relay_*` 的「临时目录当共享根」思路，把「共享根」换成「回环连接」即可。

### 12.4 测试入口

新增测试组进 `tests/run_all.py`（如 `Relay TCP Carrier`）。共享目录的既有 26 组 `test_relay_*` 保持登记、保持通过。

### 12.5 载体特性专项测试

| 专项 | 用例 | 载体 |
|---|---|---|
| 文件传输流式 | 大文件（接近 `MAX_BYTES`）、传输中断/重连续传、**完成前目标端不可见**、SHA256 校验一致、多文件目录结构保留 | tcp（SMB 回归原整包路径） |
| TCP 认证 | 错误 `sharedKey` 被拒、未认证连接不能发任何帧、重放旧代次被拒 | tcp |
| 监听边界 | 绑定指定网卡而非 `0.0.0.0`、非回环局域网地址可连、非可达网络连不上 | tcp |
