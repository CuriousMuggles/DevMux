# 文档索引与引用链

一个主题只允许有一个权威文档；其余位置只能链接过去，不能复述。改文档前先看这张表，确认改的是权威源还是引用点。

## 仓库布局

- 根目录只保留**规则入口与仓库惯例文件**：`AGENTS.md`、`README.md`、`LICENSE`。
- 其余文档全部放 `docs/`，按功能分区：`用户/`（随包）、`internal/设计|流程`、`runs/`（本地任务记录）。
- 随包文档在仓库里放 `docs/用户/`，交付时由 `doc_links.DOC_SOURCES` 映射回用户熟悉的扁平位置（ZIP 根与 `docs/` 子树）。

## 随包文档（`doc_links.DOCUMENTS`，会进 ZIP 和 `dist/`）

| 交付位置 | 仓库源文件 | 读者 | 唯一权威的内容 | 引用了谁 |
|---|---|---|---|---|
| `README.md` | `README.md` | 首次接触的人 | 项目定位、能力一览、下载与启动、构建入口 | 使用说明、开发者说明、发布说明、第三方许可 |
| `使用说明.md` | `docs/用户/使用说明.md` | 使用者 | 安装、接入目标、终端与布局、文件传输、跨机中转（步骤+状态+权限+接管）、串口与 PowerShell 的界面操作、继电器与 DB、诊断与清理、插件安装、常见问题、数据与升级 | README 不回指；自动化接入指向开发者说明 |
| `开发者说明.md` | `docs/用户/开发者说明.md` | Agent 接入方、插件开发者 | MCP/CLI 注册与工具表、认证与限额、扩展与串口动作、插件 SDK/权限/打包/发布规范 | 使用说明（只链接不复述操作） |
| `发布说明.md` | `docs/用户/发布说明.md` | 使用者、升级前必读 | 每个版本的实际变化与升级要求 | 无 |
| `LICENSE`、`第三方许可.md` | `LICENSE`、`docs/用户/第三方许可.md` | 分发者 | 授权与第三方组件清单 | 无 |
| `vendor/usb-relay/来源记录.md` | 同左 | 分发者、合规核对 | 继电器 DLL 的上游来源与摘要记录 | `第三方许可.md` |

随包文档的硬约束：**交付位置的相对链接必须闭合**（`doc_links.check_delivery` 校验），否则解压后的 ZIP 会出现死链。仓库源文件位置可以自由调整，改完只需更新 `DOC_SOURCES`。

## 本地任务记录（不入库）

- 每个任务一个目录：`docs/runs/<日期-任务简称>/`，六张卡（结论/需求/方案/验证/交付/决策）。
- 主仓已忽略该目录；`docs/runs/` 自身是独立本地 Git 仓库，可本地提交，需要备份再推私有远端。
- 任务结论回写权威设计文档；`runs/` 只保留过程与评审凭据。

## 规则

1. **一主题一权威源**：改行为先改权威文档，再改引用点的措辞。不允许两处各写一套步骤。
2. **新增随包文档**：同时加进 `doc_links.DOCUMENTS`（交付位置）、`DOC_SOURCES`（仓库源文件）、本表、`README.md` 的文档表；跑 `tests/test_docs_version.py`。
3. **新增内部文档**：放 `docs/internal/<设计|流程|历史>/`，在本表登记，不从随包文档里链接（可用纯文本提及路径）。
4. **改文件名或位置**：全仓搜索旧名；随包文档同时更新 `DOC_SOURCES`；`py doc_links.py` 必须零问题。
5. **版本变化**只写 `发布说明.md`；使用说明里出现版本化小节会被测试判失败。
6. **文件名用中文**：「对象+文档类型」两段式，如 `开发者说明.md`、`跨机中转设计.md`、`来源记录.md`。中文名对 ZIP、`docs/`、`git` 均已验证可用，`tests/test_docs_version.py` 会拦住新出现的英文名文档。例外只有四个：`README.md`（GitHub 仓库首页约定）、`LICENSE`（授权文件惯例）、`AGENTS.md`（Agent 工具约定）、`vendor/usb-relay/source/README.md`（上游原文件，不改动）。
7. **方案先定稿再开工**：非琐碎功能或架构改动，按 `docs/internal/流程/方案评审模板.md` 出方案并过评审门禁；方案处于「评审稿」时不得开始实现。最终设计与决策结论回写到对应权威设计文档，模板本身不复述方案内容。
8. **评审产物不入库**：每个任务的六张卡放 `docs/runs/<日期-任务简称>/`（已在 `.gitignore`），不登记本表、不进发布包；结论仍以权威设计文档为准。
9. **内部文档用仓库根相对路径**：`docs/internal/` 内的链接一律写成 `/docs/...`、`/relay/...` 这种以 `/` 开头、从仓库根起算的路径，不再使用 `../` 链（目录一搬就断）。随包文档保持“交付位置”的相对写法，因为发布包解压后没有仓库结构；`doc_links.py` 同时支持两种解析。
10. **具体方案与模板分开管理**：模板、规范、评审门禁入库；某个任务的具体方案放 `docs/runs/`，默认不入主仓。需要版本管理时，把 `docs/runs/` 单独 `git init` 成嵌套仓库（主仓已忽略），本地提交即可，需要备份再推私有远端，不影响主仓与发布包。
11. **分类判据**：按「生命周期 / 是否定义契约 / 是否被代码与索引引用」判断，而不是按「写得多具体」。
    - 模板、规范、流程：长期有效、定义格式 → 入库。
    - 长期设计：定义行为或接口契约、被代码注释或本表引用 → 入库。
    - 一次性方案：服务单个任务、有明确起止（阶段表、六张卡、评审记录） → `docs/runs/`，不入主仓。
    同一文档混合时拆分，不要整体搬运：契约留入库侧，任务计划与执行记录进 `runs/`。
12. **用户手册是全集，开发者手册是补集**：
    - 用户手册（`使用说明.md`）必须覆盖用户能触达的**全部功能与操作**；只读这一份就能完成所有使用场景，不得要求用户再翻开发者手册才能操作。
    - 开发者手册只写“用户手册之外、开发/接入才需要”的增量内容：接口、参数、错误语义、权限与限额、SDK、打包与发布规范。
    - 两者共有的同一事实只写一次：用户手册写**可观察行为**，开发者手册写**调用形式**，并用一节链接指向行为，不复述步骤。
    - 判定方法：新增用户可见功能 → 用户手册必须有对应章节；新增接口/参数 → 开发者手册必须有对应条目。缺任一项视为文档未完成。
